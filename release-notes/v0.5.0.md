Restow 0.5.0. Released 2026-11-18, channel beta.

Beta release. Run it alongside your existing backups, not as your only one, until
you have verified restores against your own data.

### Summary

Restow 0.5.0 restores whole Linux machines onto new hardware from a recovery ISO and proves it
first: a boot probe starts each backed up machine on other hardware in a lab and only then calls
it green. Alongside come restic repositories on copy targets that can become the primary, a
billing API for PSA tools, branded mails and reports, Proxmox VE selection by node, SQL Server
backups of Windows machines (preview) and many fixes. The update runs thirty-two database
migrations, and owners of the provider team receive critical events by e-mail from now on: read
Breaking Changes and Upgrade Notes before you update.

### Breaking Changes

- Phones are no longer a supported surface: on a smartphone every page shows a block page
  instead of the app (see Changed). Use a computer or a tablet.
- "Delete every backup" of a revoked machine is now delayed by seven days and may be requested
  only by an owner of the provider team, with a reason (see Changed). Scripts that called the
  removal with mode `delete` as a tenant administrator now get a refusal; the backups are no
  longer deleted at once.
- The agent no longer backs up its own state file, and LUKS key files are hidden from restore
  operators (see Changed): a restore of `/etc/restow-agent/state.json` from an older snapshot is
  refused with `endpoint-restore-path-locked`.
- Every owner of the provider team receives the critical events and the installation's own events
  by e-mail without opting in; an installation without a mail transport shows a lasting delivery
  failure alert until one is configured or the notification mail is marked as not needed.
- Whole machine backups of Linux machines are offered at once (the job switch "Whole machine");
  `RESTOW_BAREMETAL_PREVIEW=false` for the api hides them again.
- The integration API contract moves from 1.9.0 to 1.10.0; every change is additive (new
  endpoints, scopes and fields), and a tenant key can no longer carry the new provider-only scope
  `billing:read` (`api-key-scope-provider-only`).

### Changed

- The menu entries that lead to a restore ("Restore explorer", "File restore") carry a
  turn-back arrow in a Lapis circle at their right end, beside their own icon, so the way back to
  data stands out. Lapis, not green: green stays proof of a passed restore check.
- Public demo: Postgres is set up for its 512M limit (`max_connections=64`, `shared_buffers=64MB`,
  small `work_mem` and `maintenance_work_mem`, two autovacuum workers), and api, worker and
  scheduler open smaller pools, 48 connections in all instead of the default 90
  (deploy/demo/README.md, "Resource limits").
- The agent no longer backs up its own state file (`/etc/restow-agent/state.json`) with the agent
  secret and the repository password, on any system; the restore dialog hides it in older
  snapshots, and LUKS key files are no longer downloadable for the restore role. The browser hides
  the state file from everybody and the key files that a machine's layout names from restore
  operators; selecting one is refused (422 or 403 `endpoint-restore-path-locked`), a folder ZIP
  leaves them out, and an administrator gets a key file only after a recent sign-in, audited as
  `endpoint.repository.secret_file_revealed`.
- With `RESTOW_BAREMETAL_PREVIEW` on, the machine list and the enroll dialog no longer say there is
  no bare-metal restore: Linux machines can be restored as a whole on new hardware (preview);
  there are still no disk images.
- The recovery ISO now comes from the instance itself: the worker fetches the ISO of the
  installation's own release from the GitHub release once per installation and release (queue
  `endpoint-recovery-iso`, every six hours, resumable, at most 2 GiB, honouring `HTTPS_PROXY` and
  `NO_PROXY`), checks the signature of the release's `SHA256SUMS` itself with the release key of
  the image (the same SSHSIG check as the agent, no new trust root) and the ISO's SHA-256, keeps it
  in the data volume (`RESTOW_RECOVERY_ISO_STORE_DIR`, default `/data/recovery-iso`) and offers it
  to tenant administrators at `GET /api/v1/recovery-iso/file/<file>`; the GitHub release stays the
  fallback link. `GET /api/v1/recovery-iso` adds `rebuild`, `githubUrl`, `sumsUrl`,
  `signatureUrl` and `local` (not fetched, fetching with bytes, verified, failed with a reason,
  disabled), and the bare metal wizard shows that state in English and German. `verified` now
  means the server checked the signature itself; before, a `.sig` file next to the checksums was
  enough. The download needs the rest of the ISO plus 1 GiB free in the store and keeps that
  reserve while it runs; short of it, or on a full disk, it removes its partial file and reports
  `store_full` without retrying until the next pass. One pass works at a time (a lock file in the
  store), and a pass ends itself half an hour before the queue's eight-hour expiry so the retry
  continues the partial file instead of writing it at the same time. Installations without
  internet access drop the ISO into `<store>/import/` or `RESTOW_RECOVERY_ISO_DIR`; the same check
  applies, an unreachable release page is then no problem and no reason to retry, and the wizard
  says the copy was put there rather than fetched. `RESTOW_RECOVERY_ISO_FETCH=false` turns the
  download off. `GET /install/recovery/<v>/<file>` (10 downloads per address and hour) serves the
  same selection. The check commands name the arguments of `verify-agent-signature.sh` in their
  right order and the checksum file the ISO is listed in.
- Rebuilds of the recovery ISO: a tag `recovery-v<v>.<n>` (`.github/workflows/recovery-rebuild.yml`)
  rebuilds only the ISO of the published release `<v>` against a newer Debian snapshot (security
  updates), with the agent of that release, twice and through every end-to-end case, and publishes
  `restow-recovery_<v>.<n>_amd64.iso` with `recovery-SHA256SUMS`, which the maintainer signs with
  the release key (`scripts/release/sign-agent.sh recovery-v<v>.<n> --iso <rebuilt ISO>`). The
  list binds the rebuild to the release (`release/agent-SHA256SUMS` with the SHA-256 of the
  release's signed checksums); installations of `<v>` take the newest rebuild that verifies and
  never one for another release. `integrations/recovery/build.sh` and `sources.sh` take
  `--rebuild <n>`.
- The explanations of `snapshot_failed` and `snapshot_unavailable` no longer speak of the shadow
  copy only: they name it, LVM and btrfs, and the steps cover Windows and Linux.
- The agent's systemd unit allows mount namespaces (`RestrictNamespaces=mnt`) so the snapshot
  helper can build the LVM and btrfs snapshot tree in a private one; every other namespace type
  stays blocked.

  delayed and owner-only. The backups are deleted seven days after the request, not at once; the

### Security

- Repository pruning waits while a recovery runs; redeeming a code, trying a dead code and
  rebinding a machine alert the tenant admins. Retention and the removal of a machine's backups
  check for a running recovery session before and after they take the repository's lock, and a
  session is released only under the shared lock, so neither order prunes beneath a restore; a
  session that waits for its release holds nothing. Removing a machine (or scheduling the deletion
  of its backups) is refused while a recovery session reads it, and its unredeemed codes are
  revoked; the deletion that starts seven days later waits for a running session as well. The new alerts
  `endpoint.recovery.started`, `endpoint.recovery_code.rejected`, `endpoint.rebound` and
  `endpoint.recovery.failed` are errors of the group "Recoverability" and go to the bell and to
  every rule that lists them. Recovery codes, rebind tokens and the 64-digit hex values of a
  session are removed from every stored log and failure text.
- The download of the recovery ISO takes over a stale lock of its store atomically: the old lock is
  renamed aside and dropped only when it is still the stale one, so two passes that both find it
  stale never both write the partial file, and a pass checks that the lock is still its own before
  every write and stops without writing once it is not.
- `pnpm audit` (CI and release smoke) leaves out GHSA-fc5q-39xc-vjpf (picomatch, regular
  expression denial of service with crafted glob patterns), for which no fixed version exists.
  picomatch reaches the dependency tree only through the test runner; no Restow code and no
  production package calls it, and the production images no longer contain it (the build stops if
  it is left). The CI fails as soon as a fix is published (docs/CI.md "Audit exceptions").

### Upgrade Notes

Thirty-two database migrations (0073 to 0104) run on start: 0073 creates the new table `storage_samples` and 0074
the new table `directory_memberships`; neither rewrites anything. 0075 serves the restore
explorer's "From the archive": an index on `archive_items` (tenant, mailbox, capture time), the
index on `archive_item_mailboxes` (tenant, mailbox) replaced by one that adds the time of the
assignment, a partial index on the Message-IDs of `manifest_versions` (mail only), and the new
column `tenants.journal_address_issued_at`, empty for every tenant. Building the indexes reads the
archive's rows, its assignments and the backup index's mail rows once, and new captures and
backups wait for it meanwhile; nothing is rewritten. A journal address issued before 0.5.0 no
longer brings the menu entry "Archive" on its own: up to 0.4.12 the tenant page and the Archive
page issued it when they were first opened, also where journaling was never set up. Such a
tenant gets the entry once a journal report arrives, a mail job archives, or an administrator
opens the journal setup on the Archive page (it stays reachable by its address) or issues a new
address there; the address itself keeps working. 0076 adds three nullable columns to `pve_guests`
(`repository_reconciled_at`, `smbios_uuid`, `retired_at`) without a rewrite and rebuilds the
unique index on cluster and VMID once, now for guests that are not retired; every container's
repository is compared with its restore points once after the update. 0077 adds nullable
columns to `pve_runs`, `file_share_runs`, `pve_guests` and `pve_snapshots` and creates the table
`storage_repository_repairs` without rewriting a table; after the update, scan the repositories
of every tenant that ever changed its primary (see Fixed). 0078 adds the nullable columns
`pve_guests.repository_prefix`, `file_shares.repository_prefix` and
`settings.default_storage_write_once`, empty for every row, without a rewrite. A repository counts
as write-once only once a test of this version found it so: after the update, run "Test" on every
repository (and on the installation default) that lies on a WORM share, so that retention stops
trying to delete there and a reset begins its new chain under a fresh prefix at once. 0079
creates the new table `job_cursor_entries` (a restore job's record of what it restored) and a
trigger on `jobs` that empties it for a job that ends; nothing is rewritten. 0080 to 0088 serve
the mail archive: 0080 adds the nullable column `archive_capture_streams.backfill_cursor`; 0081
creates the type `archive_capture_gap_kind` and the table `archive_capture_gaps`, 0083 the table
`archive_chain_tombstones` and 0084 the table `archive_record_deletions`, all new and empty; 0082
adds a partial index on `archive_items` (tenant, end of retention, id) for the items with an end
of retention, and 0086 the nullable column `archive_items.report_hash` with a unique partial index
on it; 0085 adds the columns `attempts` (0 for the existing rows), `last_error` and
`last_attempt_at` to `archive_capture_pending`; 0087 adds the value `backfill_folder` to
`archive_capture_gap_kind`, and 0088 the column `archive_capture_gaps.last_attempt_at`, taken from
`last_seen_at` for gaps already recorded. Building the two indexes reads the rows of
`archive_items` once, and new captures wait for it meanwhile; no table is rewritten. 0089 creates
the new tables `installation_restore_mode` (installation-level) and `storage_progress`,
`storage_progress_checks`, `restore_mode_refusals` and `key_mirror_findings` (under Row Level
Security like every tenant table); it changes no existing table and writes no row (a tenant
without a row in `storage_progress` counts as 0). 0090 creates the new tables
`cluster_join_tokens` and `cluster_nodes` (installation-level, no Row Level Security) and widens
the check on `installation_restore_mode.source` by `setup`; both are new and empty. 0091 serves
the notifications and branding of 0.5.0 (see below). 0092 creates the new tables
`endpoint_sql_databases` and `endpoint_sql_backups` (Row Level Security) for SQL Server backups of
Windows machines and adds values to the enums of endpoint run, task and report kinds; both tables

lab"). The first directory sync after the
update reads the owners and members of every Microsoft 365 group once (three Graph reads per group, through
`$batch`); until it has run, a person's "Teams & sites" is empty and says that it may be
incomplete. Whole machine backups are offered at once; `RESTOW_BAREMETAL_PREVIEW=false` for the
api hides them again. Agents before 0.5.0 ignore `snapshotOnFailure`, `wholeMachine` and `fsSnapshot`, and the
release key keeps the fingerprint `SHA256:2LB7RPpIS0wqbcZ2NA8MjuQN7ZfFPqBX3CwrGFSu76o`. Once the
release carries a recovery ISO, the worker downloads it (under 900 MiB, leaving at least 1 GiB
free) into the data volume once, in the background, and again only for a newer rebuild; set
`RESTOW_RECOVERY_ISO_FETCH=false` to keep it from doing so.

Migration 0091 (0.5.0 notifications and branding) creates the tables `report_events`,
`provider_notification_recipients`, `provider_report_rules`, `provider_branding`,
`tenant_branding` and `branding_images`, makes `report_deliveries.tenant_id` nullable and adds
nullable or defaulted columns to `report_deliveries`, `report_rules`,
`tenant_notification_recipients`, `tenant_contacts`, `webhooks` and `settings`; no table is
rewritten. It moves the weekly report rule of the tenants' notification recipients to the
calendar week (also when the migrating owner is bound by Row Level Security). After the update
the owners of the provider team receive the critical events and the installation's own events by
e-mail; an installation without a mail transport shows a lasting "notification mail cannot be
sent" alert until a transport is configured, unless the notification mail is marked as not
needed. Before you brand a From address on SMTP, add it (or its `@domain`) to the allowed
sender addresses of the notification mail and let your mail server send as it.

From this release on every storage target gets small progress markers under
`tenants/<tid>/progress/`; they are never copied or counted, and the storage check prunes old ones
on mutable targets. Restore mode never comes on by itself after the update: a target without
markers triggers nothing. Rolling back below 0.5.0 with migrations cannot use restore mode;
docs/UPDATING.md ("Rollback") says how to keep that version from deleting.

- Proxmox VE nodes that ran a VM restore, restore check or VM boot test since their last reboot
  refuse the update to this release: their current restow-pve still counts the leftover restore
  log as a running restore (see Fixed). On such a node run `rm -f /run/restow-pve/restore/*.log`
  as root once (or reboot it, or run the installer again), then the update installs by itself,
  with **Update now** or with `/opt/restow-pve/bin/restow-pve update`.

### Known Issues

- Windows is a preview: x64 only, no Authenticode signature on `restow-agent.exe`,
  `restic.exe` or `windows.ps1` (Defender, Smart App Control and ASR rules may block them;
  each prerelease is submitted to Microsoft by hand), and it is tested on real machines only
  through the maintainer checklist in docs/WINDOWS-AGENT.md.
- A shadow copy makes a backup file consistent, not application consistent: SQL Server or
  Exchange files are crash consistent; use a pre hook for a dump.
- No alternate data streams (no Mark of the Web after a restore), no EFS files of other users,
  online-only cloud files are left out, junctions inside a backed-up folder are backed up as
  links, no system state or registry, no bare-metal restore for Windows, and further data
  drives are not reported as data folders yet.
- Bare metal (preview): Windows bare metal comes later; no change of the storage stack (BIOS to
  UEFI is a 0.5.x candidate); no Wi-Fi, VLAN or bonding in the recovery ISO; TPM2 and FIDO2
  bindings must be enrolled again; raw logical volumes (the VM disks of a Proxmox VE host) are
  not backed up; amd64 only. The recovery ISO never restores onto SAN LUNs (Fibre Channel,
  iSCSI) or removable disks yet, an unattended run (`--answers`) cannot keep an encrypted volume
  (the old passphrase is asked on the console only), and the details of an error (the message
  of a failed command or request) are shown in English on a German console. The first
  `packages.lock` of the recovery ISO is written by the CI
  job `recovery-iso` (input `update-lock`) and committed by hand; until then the ISO is not
  built, and it counts as reproducible only once two CI builds were equal. The ISO download of the
  instance does not support a proxy that is itself reached over https (`HTTPS_PROXY=https://…`),
  and the rebuild workflow and the signing of a rebuild have not run against a real release yet.
- Bare metal restore is tested in the CI for Debian 12 and 13 and Ubuntu 22.04 and 24.04 only.
  AlmaLinux and the RHEL family, Fedora, openSUSE Leap and Arch Linux are meant to work but are
  not tested yet (their test machines come from cloud images, which the test driver cannot build
  yet); the assessment calls them "untested distribution". A test restore onto spare hardware
  tells before you rely on it.
- Bare metal restore is proven in the CI only (QEMU/KVM, see Verification), not yet on real
  hardware: the maintainer checklist of docs/BAREMETAL.md 21.4 has not run for this release.
  Test a restore of your own machines onto spare hardware before you rely on it.
